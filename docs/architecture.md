# Architecture

AutoFlowOps is a self-hosted automation dashboard with a FastAPI backend, a React frontend and PostgreSQL persistence. The MVP intentionally keeps a minimal runtime: one API process owns the REST API, the APScheduler scheduler and HTTP job execution.

---

## Runtime Components

| Component | Responsibility |
| --- | --- |
| **Frontend** | Browser UI — dashboard, webhooks, alerts and reports |
| **Backend API** | REST API, request validation, database access and operational workflows |
| **PostgreSQL** | Persistent storage for all domain data |
| **APScheduler** | In-process interval and cron scheduling for active jobs |
| **HTTP runner** | Executes HTTP jobs with timeout, stores masked request/response data |

---

## High-Level Request Flow

```text
Browser
  └─> React/Vite frontend (port 3000)
        └─> FastAPI REST API (port 8000)
              ├─> SQLAlchemy async session
              │     └─> PostgreSQL (port 5432)
              ├─> APScheduler (in-process, background thread)
              │     └─> HTTP runner
              └─> Webhook receiver
```

---

## Data Model

The initial Alembic migration creates these tables:

| Table | Purpose |
| --- | --- |
| `jobs` | HTTP job configuration, schedule metadata, last/next run timestamps |
| `executions` | Execution history: request metadata, masked headers/body, response previews, errors |
| `webhooks` | Inbound webhook definitions: slug, hashed token, status |
| `webhook_events` | Individual events received at each webhook endpoint |
| `alerts` | Internal operational alerts generated by failures or created manually |
| `reports` | Saved canonical report content (JSON) and metadata |
| `users` | Reserved for future authentication and ownership features |

## Scheduling Model

The scheduler is loaded at backend startup and persists across the process lifetime.

| Schedule type | Expression format | Example |
| --- | --- | --- |
| `manual` | None — triggered only via `POST /api/jobs/{id}/run` | — |
| `interval` | Seconds as a plain integer string | `"300"` → every 5 minutes |
| `cron` | Five-field crontab expression | `"*/10 * * * *"` → every 10 minutes |

When a job's status changes to `paused` it is removed from the scheduler. When it returns to `active`, it is re-registered with the same expression.

> **Multi-instance note:** The in-process scheduler is designed for a single backend replica. To run multiple backend replicas or heavy job loads, migrate execution to a Celery/Redis worker (see [Roadmap](roadmap.md)).

## Flow: HTTP Job Execution

### Manual trigger

```text
POST /api/jobs/{id}/run
  └─> load job from DB
        └─> http_runner.run_job_http(job, session)
              ├─> httpx.AsyncClient.request(method, url, headers, body, timeout)
              ├─> mask sensitive headers and body fields
              ├─> create Execution record (status, timings, masked request, response preview)
              └─> if status == "failure"
                    └─> create Alert record (severity="error", source_type="job_execution")
```

### Scheduled trigger

```text
APScheduler fires _run_scheduled_job(job_id)
  └─> open async DB session
        └─> load job from DB
              └─> http_runner.run_job_http(job, session)
                    ├─> (same as manual trigger above)
                    └─> update job.next_run_at from scheduler
```

## Flow: Webhook Reception

```text
POST /api/webhooks/{slug}/receive
  ├─> look up webhook by slug → 404 if not found
  ├─> check webhook.status == "active" → 403 if paused
  ├─> validate X-Webhook-Token header against SHA-256 hash → 403 if mismatch
  ├─> mask sensitive headers and payload fields
  ├─> create WebhookEvent record (headers_masked, payload, source_ip, received_at)
  ├─> update webhook.last_received_at
  └─> return 200 with event id
```

Reprocessing an event replays the stored payload through the same masking and storage pipeline without re-validating the token.

## Flow: Alert Generation

Alerts are created automatically by the HTTP runner on every failed execution:

```text
run_job_http detects execution.status == "failure"
  └─> create Alert(
        title      = "Job '<name>' failed",
        message    = error_message or f"HTTP {status_code}",
        severity   = "error",
        source_type = "job_execution",
        source_id  = execution.id,
        status     = "open"
      )
```

The alert lifecycle is then managed manually:

```text
PATCH /api/alerts/{id}/acknowledge  → status: "acknowledged", acknowledged_at: now
PATCH /api/alerts/{id}/resolve      → status: "resolved",     resolved_at: now
```

## Flow: Report Generation

```text
POST /api/reports/generate
  ├─> validate period_start <= period_end
  ├─> query executions in the period from DB
  ├─> query alerts in the period from DB
  ├─> compute:
  │     - total/success/failure counts
  │     - success rate
  │     - average duration
  │     - top failed jobs
  │     - recommendations
  └─> serialise canonical JSON content
        └─> create Report record (name, format="json", period, content)

GET /api/reports/{id}/download?format=json|markdown|csv
  └─> load Report.content from DB (no recomputation)
        └─> render to requested format and stream as file download
```

Reports are derived from their saved canonical JSON, so historical reports remain stable even after new executions are created.

## Security Model

| Concern | Current approach |
| --- | --- |
| Secrets in logs | Sensitive headers and JSON body fields masked before any DB write |
| Webhook tokens | Stored as SHA-256 hashes; plain tokens never persisted |
| `.env` file | Git-ignored; only `.env.example` is committed |
| Authentication | None in the MVP — intended for private networks, VPN or reverse proxy setups |
| SSRF | No explicit blocking in the MVP; validate job URLs before use in production |

See [docs/security.md](security.md) for the full masking reference.

---

## Known MVP Boundaries

- **No authentication.** All API endpoints are open. Do not expose the backend publicly without a reverse proxy or network-level access control.
- **In-process scheduler.** APScheduler runs inside the backend process. Best suited to a single replica deployment.
- **One request per execution.** Retry settings are persisted for future worker behavior; the current HTTP runner performs one request per execution.
- **Frontend is API-first.** The dashboard, webhooks, alerts and reports pages are implemented. A jobs management UI (create/edit/list) is planned for a future phase.
- **Reports are not recomputed.** Downloads are generated from the saved canonical JSON, not recalculated from live data.
